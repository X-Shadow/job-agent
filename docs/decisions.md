## 2026-09-28 · 选题：课程资料问答 → 求职助手 Agent

**背景**

先按「课程资料问答助手」方案建好了骨架（README、`eval/questions.csv` 三类问题、基础 RAG 脚本），
之后决定换成「求职助手 Agent」。

**候选方案**

- **A. 课程资料问答助手** —— 用我自己课程资料做问答，重点做幻觉检测与拒答
- **B. 求职助手 Agent** —— 粘贴 JD → 解析 → 匹配经历库 → 改写建议 → 跟踪投递

**我选了**：B

**理由**

1. **面试官能当场验证**：他天天招人，一眼就能判断我的匹配逻辑合不合理；
   而课程资料问答他不懂我的课程资料，只能听我单方面说
2. **真实用户**：我自己每天在投简历，B 的每个功能我都在用；
   A 做完之后没有任何真实使用数据
3. **真实指标**：B 能拿到"投递回复率"这个可验证的外部指标；
   A 只能拿到自己出题自己测的准确率

**代价**

- 要先把经历库整理出来（A 的资料是现成的，省这一步）
- 匹配度的评估偏主观，指标设计比 A 难

**放弃了什么**

课程资料问答方案里已经设计好的**三类问题结构**（事实型 / 推理型 / 边界型）——
设计思路保留，但换成 JD 测试集。已整理的课程资料本身不再使用。

**怎么验证的**（写方法，不写结论）

- Day 10：自己真实投 20 个岗位，全程使用本工具，记录每一步的失败案例
- Day 12：人工抽检 20 条 requirement 判定，算匹配一致率
- Day 12：对比"用工具改简历前 / 后"各投 20 家的回复率

**AI 在这里做了什么**

帮我分析了两个选题在「可验证性 / 真实用户 / 评估难度」三个维度上的取舍。
方案对比是 AI 提供的，**最终选择是我做的**。

## 2026-10-02 · parse_jd 首跑质量判定

**背景**：首个真实 JD（社招·AI应用开发）解析一次通过，1036 tokens

**两个决策**
1. keywords 保留上下位冗余（向量数据库/Milvus/Qdrant 不去重）
   我选保留，理由：这样做更保险，用户写的哪一个词就用哪一个词去检索
2. must_have 粒度："学历+专业"合为一条不拆
   我选不拆，理由：在简历里通常写在一起，拆开会变的碎
**怎么验证的**：人工逐条检查 8 条 must_have、18 个 keywords；
red_flags 对社招 JD 返回空数组，确认模型"不硬凑"行为符合设计

## 2026-10-02 · 提示词规则有效性实验（规则4：keywords 写法约束）

**实验设计**：同一份 JD，删/加规则 4 各跑一次，其余不变
**观察**：有规则时 keywords 更标准化（Prompt Engineering 替代中文、
去掉照抄词 skills、聚焦核心词）；nice_to_have 的差异判定为运行波动
**结论**：规则 4 有效，保留
**局限**：单次实验、n=1，结论是方向性的而非统计性的


## 2026-10-03 · 13 条数据要不要向量检索（Day 3 决策，补记）

**背景**：经历库仅 13 条，肉眼翻 JSON 也能找，向量检索在这个量级是"超配"

**选项**
- A. 不建检索，全量塞给 LLM
- B. 向量检索（Chroma + 智谱 embedding-3）
- C. 关键词匹配 BM25（任务清单预留，Day 10 对比用）

**我选了**：B

**理由**：
1. **它是核心链路的一环**：下游逐条匹配判定（score_match）的输入就是检索结果，
   没有这一步，判定就没有依据
2. **数据会长大**：真实投递过程中经历库会持续增补，到几十条时
   "全量塞给 LLM"的成本和注意力稀释都会成问题
3. **能力对齐**：RAG / 向量检索写在目标岗位的硬性要求里，
   这是能落地的实践证据，不是概念
4. **我知道它是超配**：13 条规模下确实可以不建检索，
   选 B 是"为数据增长铺路"，不是"这个量级必须用向量检索"

**代价**：
- embedding 单次调用 400~600ms（当时用智谱 API）
- 经历库更新后**必须重建索引**，否则检索结果与真身不一致
- 多了一个外部依赖——后来智谱余额不足时整条检索链路直接不可用，
  这也是后来换成**本地模型**的直接原因

**怎么验证的**：6 组真实查询的距离分桶——明显相关 <1.0，凑数 >1.1（n=6，体感非统计）；"FastAPI 后端"组全员 >1.0，诚实暴露库存量缺口

## 2026-10-03 · 检索方案初测

**现象**：6 组查询中 4 组 Top-1 正确，2 组错误。

**规律**：
- 含精确技术名词的查询（Git / RAG / 嵌入式 / Agent）→ Top-1 全部正确
- 口语化查询（"FastAPI 后端"、"用 Python 做 Web 后端接口"）→ Top-1 全错，
  正确答案被表面词（"Web"、"Git"）顶下去

**初步结论**：纯向量检索在"人话查询"上会退化为词汇邻近匹配。

**怎么验证**：Day 12 按 query.type（term / natural）分组，对比 BM25 / 向量 / 混合三种命中率。

**AI 在这里做了什么**：无。这 6 条查询是我手写的，bad case 是我一条条看出来的。

## 2026-10-03 · 检索窗口丢失关键条目 → 决定全量输入

**背景**：exp_001 bullets 更新重建索引后排名漂移，exp_009（唯一的 Python/MySQL 证据条）掉出 Top-5，判定器"失明"

**选项**
- A. k=全库条数（动态 count）
- B. k=8 折中
- C. BM25 关键词混合兜底
- D. 每条 must_have 单独检索

**我选了**：A

**理由**：可算的账：13 条规模全量输入 prompt 只多几百 token（1847→2571）；漏检一条丢一个 matched 的代价更高

**触发条件**：库到 50+ 条时收紧窗口并上 BM25 混合；C 不作废，转 Day 10 对比实验（纯向量 vs 混合的命中率对比）

**代价**：prompt 1847→2571；无关条目（志愿服务、演讲）也进了判定输入

**局限**：如：这是"当前规模下的妥协"，检索的精准价值要库变大后才兑现——诚实说，现在检索主要贡献排序而不是筛选

## 2026-10-03 · 提示词新增第 8 条：进行中 ≠ 已完成

**背景**：模型把 exp_001 bullets 里"进行中：Agent 工具循环"读成"已实现"（出现在 MCP 条目的描述里）

## 2026-10-04 · 改写建议与投递信的防夸大机制

**背景**：rewrite_section 和 generate_cover_letter 是 LLM 最容易顺手写
"精通""深入"的场景——改简历、写求职信天生有美化动机，而夸大的措辞
会在面试里变成打向候选人自己的子弹

**决策**
1. RewriteSuggestion 每条建议必填 exaggeration_risk：要写具体的追问场景
   （如"会被问 Chroma 距离度量怎么选"），禁止"注意别夸大"式废话
2. 提示词硬规则：rewritten 只能重组经历库里已有的事实，
   禁止新增不存在的项目、数字、技术词
3. CoverLetter 带 honesty_notes：正文里哪些措辞是修辞、面试要能兜住，逐条列出
4. 交付形态：信和备注一起输出，删不删由投递者决定——工具只负责把风险摆到明面上

**理由**：可参考的角度：这个工具的第一指标是"不敢编"而不是"写得好"——为什么这个排序在求职场景下成立

**怎么验证的**：首轮输出——5 条建议的夸大风险全部具体到追问点；投递信无"精通/深入/多年"，且主动坦白"没有用 FastAPI/Flask/Django 完成过实际开发"；honesty_notes 7 条，含"计划 ≠ 已有经验"的显式区分；判定器还抓到"exp_001 标签含 FastAPI 但要点无实现"的标签与内容不符

**局限**：真实存在的两个缺口，写不写你定：①风险是模型自报的，没有独立的第二遍审查；②rewritten 的事实核查目前靠人工抽查——Day 12 评估可考虑加"编造检出"抽检项

## 2026-10-04 · Embedding 后端：智谱 API → 本地 bge-small-zh-v1.5

**背景**：智谱账户余额不足，检索链路（build_index / search_experience）全部不可用；
DeepSeek 没有 embedding API，没有现成退路。此前用智谱 embedding-3（2048 维）。

**候选方案**
- A. 本地 BAAI/bge-small-zh-v1.5（sentence-transformers，权重已在 HF 缓存，零下载成本）
- B. 智谱 embedding-3 充值续用
- C. 其他云 embedding（硅基流动 / 阿里 / 百度等）

**我选了**：A，并把 B 保留成可切换后端（config 里 `EMBED_BACKEND` 常量）

**理由**：免费、离线、数据不外传；已有缓存；保留切换能力所以没锁死

**代价**：512 维 vs 2048 维，表达力可能更弱；
每次冷启动多付约 10 秒（导入 torch + 载模型）；依赖变重（requirements 110 行，torch 家族体积大）

**放弃了什么**：放弃了"零维护"——本地模型要自己管版本、管缓存、管离线配置

**怎么验证的**（数据已实测）
- 6 组固定查询对比（`scripts/compare_queries.py`）：与智谱时期**第一名判断基本一致**，差异集中在第 3-5 名
- 耗时结构：首次调用 9536ms（含导入+载模型），之后每次 8~12ms（智谱 API 为 246~592ms）
- 距离体感重建（512 维归一化 + L2）：强相关 0.42~0.67｜相关 0.9~1.0｜凑数 1.05~1.26

**踩坑记录**（若不单开一条，就写在这里）
- 现象：首次建索引 13 条文本耗时 **178482ms**（178 秒）
- 根因：huggingface_hub 对每个文件发 HEAD 请求检查更新，网络不通时重试 5 次指数退避
- 修复：`config.py` 设 `HF_HUB_OFFLINE=1` → 降至 10683ms
- 换种修法会怎样：设 HF_ENDPOINT 走国内镜像 —— 但只在需要下载新模型时才有意义，
  已有缓存时离线模式更彻底（连请求都不发）

**局限**：两轮对比之间改过 experience.json，不是干净 A/B；
13 条规模下两者都够用，真实差距要等库更大才显现

**AI 在这里做了什么**：AI 提出双后端方案与"归一化后 L2 距离"的解释，
但**切换的决策和 512 维风险由我确认**；HF_HUB_OFFLINE 的排查是 AI 读日志定位的

## 2026-10-04 · 查询指令（bge query instruction）：加还是不加

**背景**：bge 官方给出查询指令「为这个句子生成表示以用于检索相关文章：」，
但说明 v1.5 加不加差异很小、"最好在你自己任务上测"。文档侧则一律不加。

**我选了**：从实测数据看结论是"不加"

**理由**：从实测数据看结论是"不加"

**怎么验证的**（数据已实测）
- 设计：同一进程内连续跑两侧（运行时切换开关），模型实例与索引完全相同，唯一变量是指令开关
- 结果：Top-5 完全一致仅 **1/6** 组；但差异**全部落在第 3-5 名**，第 1 名只在"FastAPI 后端"
  （全库无真货的凑数组）换过
- **关键发现**：加指令后距离**系统性上移**，每组每条约 +0.10~+0.27——是统一尺度平移，不是个别变化
- 副作用：既有阈值（0.42~0.67 强相关等）加指令后全部失效，需重标

**代价 / 放弃了什么**：选择不加，等于放弃"可能与官方推荐更一致"的选项；
但保留了开关，随时可重测

**局限**：6 条查询、**无标注正确答案**，"未观察到改善"≠"证明更差"。
严格判优劣需先为每条查询定义命中标准（该标准由我制定）。
**AI 在这里做了什么**：AI 设计并执行了对照实验（同进程双侧、控制变量），
结论由数据给出；**是否采纳"不加"由我决定**

## 2026-10-04 · parse_jd 输出不稳定 → 引入运行存档

**背景**：同一份 JD（749 字符，未改）解析出的 must_have 条数在多次运行间波动。

**怎么验证的**（数据已实测）
- 连跑 3 次：must_have = 6 / 4 / 6，keywords = 34 / 32 / 30
- 温度对照：`temperature=0.1` → [5, 6, 7]；`temperature=0.0` → [7, 8, 4]
- 累计 9 次观测，must_have 落在 **4~8 条**
- 事实核对：该 JD 不带"优先"的硬性要求是 4 条 → 4 条与人工判断一致，6~8 条属拆得过细

**结论**：波动来自"逐条拆开"规则的粒度无明确边界；
temperature 降 0 无效 → 是语义歧义而非采样随机

**我选了**：不改提示词（暂），改为**给每次运行存档** ——
`data/runs/<时间戳>/{jd.txt, jdinfo.json}`，并支持 `reuse` 复用同一份 JDInfo

**理由**：must_have 条数决定逐条判定的条目数，跨运行对比会混入解析噪声；
评估的前提是输出稳定，否则测的是噪声

**代价 / 放弃了什么**：放弃了"每次跑都是全新解析"的简单性，
换来可追溯；存档会累积文件

**局限**：三次均为 deepseek-flash，此前各轮为 deepseek-chat，模型更换这一变量未控制

**AI 在这里做了什么**：AI 执行实测并发现波动；**是否改提示词、是否存档由我决定**

## 2026-10-04 · 同类缺陷根治：数据在库里 ≠ 进了消费者视野

**背景**：同一类缺陷当天出现第 3 次——LLM 工具的输入少了必要数据块：

| 次数 | 谁 | 缺了什么 | 后果 |
|---|---|---|---|
| 1 | score_match | basics | 本科被误判 gap |
| 2 | score_match | exp_block 里的 tags | Python/MySQL "经历库未提及" |
| 3 | generate_cover_letter | basics | 投递信把大四写成大三 |

**我选了**：**根治而非点修**——抽出共用块 `_profile_block(basics)`，
给 rewrite_section / generate_cover_letter 补 `basics` 参数（后者此前也漏，只是没暴露）；
数据侧给 basics 增加显式字段 `status`；提示词加"身份状态只能引用档案原文，不得推断"

**理由**：Day 4 只给 score_match 点修了一次，Day 5 新工具立刻重犯——
**只扑火没查火源**；而且这类缺陷不报错，输出看着通顺，只能靠人工对事实核验

**代价 / 放弃了什么**：多点修会更快，但会留第 4 次、第 5 次

**怎么验证的**（数据已实测）
- 修复前：投递信"我目前是大三在读"
- 修复后：标题"2027 届本科在读，可全职实习"，正文"大四在读学生，2027 届应届毕业生
  （2027.06 毕业，大四已无课，可全职实习）"——与 basics 逐字对应
- 全文核对：出现"2027 届" 2 次，无"大三"

**局限**：共用块只覆盖"档案"，其他数据块（经历/匹配结果）仍靠人工记得传；
可考虑在新增工具时加一条自检清单

**AI 在这里做了什么**：AI 做了代码修复与验证；**"根治而非点修"这一判断由我确认**
